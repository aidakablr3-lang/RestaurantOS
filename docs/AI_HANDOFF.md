Fixed to `SELECT set_config('app.tenant_id', :tenant_id, true)`, identical transaction-local semantics. User explicitly approved this as a "genuine production defect" before it was touched. Not fixed (unrelated), disclosed here and in §11/§16.
2. `6e50f68` — `fix(api): add CORS middleware so browser clients can call the API`. **Second defect, found immediately after fixing #1: admin-web's login request never reached the backend at all.** The app had no `CORSMiddleware`; every browser's preflight `OPTIONS` request got `405 Method Not Allowed` with no `Access-Control-Allow-Origin` header, so the browser blocked the real request before it was ever sent. ### P0 correction — payment/billing model and table lifecycle (2026-08-12)

**Scope:** a focused correction requested directly off the findings in `docs/RestaurantOS_Full_Restaurant_Day_Simulation_Report.md` (Run 3). Explicitly **not** a new feature sprint — no Purchasing/Inventory/Kitchen/QR work was touched. Three business-rule/architecture changes, each documented here so future sessions don't have to re-derive them from source:

**1. Tip is not part of the restaurant bill.** The customer owes exactly `food/drinks subtotal + tax + adjustments` — nothing else. `RecordPaymentUseCase` (`services/api/.../use_cases/record_payment.py`) no longer reads a `tipAmount` from the payment request at all; `RecordPaymentRequestSchema`/`RecordPaymentRequestDTO` have no such field. Every payment recorded from now on persists `Payment.tip_amount = 0`. `amountPaid` (both `GetBillUseCase` and `ApplyBillAdjustmentUseCase`'s own computation) is now simply `Σ(settled payment.amount)` — no subtraction of anything. **This directly fixes the P0 bug the simulation report identified** (Bug 1: a tipped payment that exactly covered `amountDue` never closed the bill, because the old formula credited only `amount − tipAmount` toward the bill). A related loophole was found and closed during this fix: `BillAdjustmentType.TIP` existed as a *bill adjustment* type that would have added a positive amount straight into `amountDue` — `ApplyBillAdjustmentUseCase` now rejects any attempt to apply one (`TipAdjustmentNotSupportedError`, `TIP_ADJUSTMENT_NOT_SUPPORTED` → 409). No migration: `payments.tip_amount` and the `tip`/`TIP` enum value both stay in the schema/DB (backward compatible with any historical rows), simply no longer reachable from any active write path. If a guest tips a server, that happens entirely outside RestaurantOS (cash, personal UPI, etc.) — the product does not record it.

**2. Full payment now automatically releases the table.** `RecordPaymentUseCase` gained a `table_repository_factory` dependency; when a payment fully settles a bill (`fully_paid`), it closes the order (as before) and, in the *same* database transaction, releases the order's table back to `available` if it was `occupied` — via a new shared helper `_table_release.py::release_table_if_occupied`, extracted so `CloseOrderUseCase`, `VoidOrderUseCase`, and `RecordPaymentUseCase` all share the exact same "only release if still occupied, never clobber a manual `cleaning`/`reserved`" rule rather than three copies of it. **This directly fixes the P0 bug the simulation report identified** (Bug 2: a fully-paid table stayed `occupied` forever with no automatic release). Partial payments correctly leave the table `occupied`.

**3. RestaurantOS v1 has no refund workflow.** `POST /api/v1/payments/{id}/refund` is removed from `payment_router.py` — the route simply no longer exists (a request to it now 404s). Reasoning: RestaurantOS is responsible for recording consumption, calculating the bill, recording settlement, and closing out the order/table — not for acting as a payment-provider dispute/refund system. A failed, reversed, or disputed transaction is handled entirely by the relevant payment provider/bank, outside RestaurantOS. **The abstraction is deliberately preserved, not deleted:** the `Refund` domain entity, `RequestRefundUseCase`, the repository's refund methods, and the reversing ledger logic are all still present and still unit-tested — only the REST route and its RBAC wiring are gone, so a future real payment-gateway integration has something to build on rather than starting from nothing. `billing.refund` is no longer granted to any role in `tenant_provisioning_service.py`'s default catalogue (Tenant Owner/Restaurant Manager/Branch Manager all had it before); the permission code itself is left in the `permissions` table undeleted (no migration), and any tenant provisioned before this change keeps whatever grant it already has — harmless, since there's no route left for it to authorize.

**Frontend (`apps/admin-web`):** the "Record payment" dialog now has a single "Amount to pay" field, no tip input. The bill detail page's payments table dropped its "Tip" and "Refund" columns entirely; the "Apply adjustment" dialog's type dropdown no longer offers "Tip" as an option. `types/payment.ts`/`lib/api/payments.ts`/`hooks/use-payments.ts`/`lib/schemas/bill.ts` all dropped their refund-related exports (`Refund`, `RefundStatus`, `RequestRefundRequest`, `requestRefund()`, `useRequestRefund()`, `requestRefundSchema`) and `tipAmount` from the payment-request side; `Payment.tipAmount` stays on the read side only, for backward-compatible display of any historical row. `components/payment-status-badge.tsx` dropped `RefundStatusBadge`.

**Testing:** unit tests for `RecordPaymentUseCase` gained `table_repository_factory` wiring plus two new tests (full payment releases an occupied table; partial payment leaves it occupied). The real-Postgres integration lifecycle test (`test_order_kitchen_billing_payment_router.py`) now creates its order against a real dine-in table, pays the exact `amountDue` with no tip, asserts the bill/order/table all reach their correct final state in one call, and asserts the refund route now 404s — plus two new dedicated tests: overpayment rejection, and partial-then-full payment with the table staying occupied until the final payment. Full `services/api` unit + integration suites, `ruff`, and `mypy` all re-run clean; `tsc`, `eslint`, `vitest`, and `next build` all re-run clean on `apps/admin-web`. See the session's own final verification report for exact numbers/commit hashes.

**Known follow-up, deliberately not built this pass (per explicit instruction to stop after this correction):** no Cashier role was added (still a P1 from the simulation report); refund's internal proportional split math in `request_refund.py` was left untouched since the use case itself is dormant; the EOD report's own `totalTipsAmount` metric is untouched and will simply always read `0` going forward, which is correct, not a bug.
