Not fixed (unrelated), disclosed here and in §11/§16.
2. `6e50f68` — `fix(api): add CORS middleware so browser clients can call the API`. **Second defect, found immediately after fixing #1: admin-web's login request never reached the backend at all.** The app had no `CORSMiddleware`; every browser's preflight `OPTIONS` request got `405 Method Not Allowed` with no `Access-Control-Allow-Origin` header, so the browser blocked the real request before it was ever sent. Rather than leave this as an inline migration-docstring disclosure only, the user directed a first-class ADR: it records why standard RLS cannot apply to this one table, confirms the implemented decision (no RLS on `qr_codes`, application-layer tenant scoping for the management path — the `permissions` table's existing no-RLS precedent, not a new isolation mechanism), and — the ADR's real new content — sets a full, binding contract for the Step 4+ resolution endpoint that doesn't exist yet: exactly what it may return (`{tenant_id, branch_id, table_id}`, nothing else), what it must never expose (menu/restaurant/branch display data, RBAC data, any error detail that distinguishes "not found" from "revoked"), token validation, opaque/non-sequential token generation, rate limiting, enumeration/brute-force protection, audit/abuse-monitoring, and — critically — that resolution confers zero elevated trust: every downstream authenticated or guest operation must still pass through the normal `TenantContext`/RLS/RBAC stack unweakened. **No database design changed; no API added; no new infrastructure (e.g. an RLS-bypass role) introduced** — this is a documentation-only pass, explicitly scoped by the user to precede Step 4 rather than be decided ad hoc once Step 4 is under time pressure. **User-approved:** "I approve the current `qr_codes` no-RLS implementation for now."

The audit surfaced two genuine, real MEDIUM-severity findings — not architecture gaps, pure API-contract/DX issues — which the user asked to be fixed before frontend work begins:

1. **`422` validation errors didn't use the standard envelope.** FastAPI's own built-in `RequestValidationError` handler was never overridden, so it returned its raw `{"detail": [...]}` body — the one response shape in the entire API that didn't match the `{success, data|error}` envelope every other route uses. Confirmed empirically (an actual request, not just reasoning about it) before and after the fix. **Fixed** (`cf79bd0`): a `RequestValidationError` handler in `core/exceptions.py` that collapses Pydantic's error list into the same `{success:false, error:{code:"VALIDATION_ERROR", message}}` shape as every other error — `message` joins each `location: reason` pair with `"; "` rather than inventing a second, structured per-field error shape on the shared envelope.
2. **No OpenAPI `securitySchemes` were declared anywhere.** Auth is a raw `Authorization` header dependency (`require_authenticated_user`), not `fastapi.security.HTTPBearer`, so FastAPI never auto-populated `security` in the schema — nothing machine-readable distinguished the one public route (`GET /api/v1/qr/{token}`) plus `login`/`refresh`/`logout` from the other 69 Bearer-gated operations. **Fixed** (`5db33c9`): a `custom_openapi()` override in `main.py` (the FastAPI-documented pattern for this) that registers a `BearerAuth` HTTP scheme and applies `security: [{"BearerAuth": []}]` to every operation except the 4 public ones. Schema-generation-time only — never touches runtime request handling, zero behavior-change risk, verified by re-running the full suite after the change (still 980 passing, plus 5 new).

**Tests** (`66c4eb0`): 5 new tests in `tests/unit/test_main.py` — 2 for the validation envelope (missing-field and out-of-range-field, both asserting the standard envelope shape and the absence of the raw `detail` key), 3 for the security scheme (scheme registration, the exact 4-route public set, and every one of the other 69 operations requiring `BearerAuth`). All pass.

**Full-suite re-verification after both fixes:** 985/985 (980 + 5 new), zero regressions, one full run (~65 minutes). `ruff format`/`check` clean; `mypy src/` unchanged (both touched files pass standalone with zero issues — the one `# type: ignore[method-assign]` on `app.openapi = custom_openapi` is a correct, necessary suppression for a legitimate bound-method override, not a swept-under-the-rug finding).
