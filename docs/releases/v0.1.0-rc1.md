## Executive Summary

This is the first release candidate for the **Tenant Platform** (Sprint
4.1) — RestaurantOS's first business platform, built on top of the Sprint
3 identity/auth foundation. It adds tenant lifecycle management (onboard,
suspend, reactivate, offboard), a platform-admin web UI to drive it, 84
backend tests, a 24-spec Playwright end-to-end suite, and the release
infrastructure (Docker Compose, CI, documentation) needed to make the
whole thing reproducible.

The RC1 hardening pass removed a committed development private key,
found and fixed a build-breaking bug in the Docker image, and found and
fixed a CORS/port mismatch that would have failed the entire CI
end-to-end job. All fixes were release-engineering only — no
application/business logic changed.

**Since that pass, the repository has been pushed to GitHub for the
first time** (`https://github.com/aidakablr3-lang/RestaurantOS`), all
three branches (`main`, `develop`, `feature/tenant-platform-frontend`)
are live with upstream tracking, and **`.github/workflows/ci.yml` has
now actually run on GitHub's infrastructure and passed** — confirming
the CORS/port fix (Playwright's `e2e` job passed) and the general
correctness of the backend/frontend jobs on real infrastructure for the
first time. See [CI Status](#ci-status) for the full run breakdown.

**Docker remains unverified** — Docker is not installed in this
environment, and the successful CI run does *not* substitute for this:
`ci.yml` uses GitHub's native Postgres service containers and direct
`pip`/`npm install` steps, not `docker compose`, so `docker-compose.yml`
and the Dockerfile are still only statically reviewed, not executed.

**Recommendation: ready to merge into `develop`, pending explicit
approval.** See [Merge Readiness](#merge-readiness) for the full
reasoning and residual risks.

## Fixes

Four fixes landed in this RC1 hardening pass, each its own commit:

1. **`7ff7a6f` — Stopped committing the dev JWT private key.** `infrastructure/docker/dev-jwt/{private,public}.pem` were tracked in git. Removed from the working tree, replaced with idempotent `generate-dev-keys.sh`/`.py` scripts that generate a local, gitignored keypair on demand. **Known limitation:** the removed files still exist in this branch's earlier commit history — this stops future commits, it does not rewrite history. See Known Limitations.

2. **`c1d4629` — Fixed a CORS/port mismatch that would have failed the entire `e2e` CI job.** `playwright.config.ts`'s `webServer` defaults to port 3100; the `e2e` job's backend was only configured to allow CORS from `localhost:3000`. Every browser request the Playwright suite made in CI would have been rejected by CORS before reaching the API — all 24 E2E tests would have failed the first time this job actually ran on GitHub. Fixed by pinning `E2E_PORT=3000` for that step. Also fixed: the CI-only `"github"` reporter wrote no report to disk, leaving the "Upload Playwright report" artifact step with nothing to upload; added the `html` reporter alongside it. Also corrected a stale doc claim in `apps/admin-web/e2e/README.md`.

3. **`b53ca56` — Fixed a build-breaking bug in the Dockerfile.** The image copied only `pyproject.toml` before running `pip install -e ".[dev]"`, intending to cache the dependency layer separately from source. This is wrong for a src-layout PEP 660 editable install: setuptools only maps files it can see at install time, so with no `src/` present yet, the editable install "succeeds" but the package is permanently unimportable — even after `src/` is copied in by a later layer. **Confirmed by reproducing the exact failure outside Docker**, then confirming the fix (copy source first, then install) resolves it. Since `alembic/env.py` imports `restaurant_os_api.core.config` at module load, this would have broken `docker compose up --build` immediately — not even migrations would have run. See [Docker Status](#docker-status).

4. **`a6aa9a0` — Documentation follow-up**, recording the Dockerfile fix in `docs/DEVELOPMENT.md`'s existing "not run against a live daemon" disclosure.

No fixes in this pass touched business logic, domain models, or the RLS/auth architecture.

- No test-coverage percentage tooling configured; coverage is qualitative (see `docs/AI_HANDOFF.md`).
- No production-shaped Docker image, staging/production deployment pipeline, or CI-enforced architecture-boundary linting — tracked in `docs/RELEASE_CHECKLIST.md`'s "Not yet in place" section as deliberate, out-of-scope gaps.
