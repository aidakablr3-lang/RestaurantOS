# Release Checklist

Run through this before merging a feature branch into `develop`, and
again before promoting `develop` into `main`. Phase 1–2 scale (per
Technical Architecture v2.0 §9.2) — no staging/production deployment
pipeline exists yet (see "Not yet in place" below), so today this
checklist governs **merge readiness**, not a live deploy.

## Before merging a feature branch into `develop`

- [ ] All commits use Conventional Commits and each one stands on its
      own (see `git log` on the branch — squash/reorder if not).
- [ ] Backend: `ruff format --check .` and `ruff check .` clean
      (`services/api`).
- [ ] Backend: unit tests pass — `pytest tests/unit -q`.
- [ ] Backend: integration tests pass against a real Postgres —
      `TEST_DATABASE_URL=... pytest tests/ -q` (see
      `docs/DEVELOPMENT.md`). Don't skip this because unit tests are
      green; this sprint's own history is exactly why (`docs/AI_HANDOFF.md`
      Step 4 — the integration suite silently never ran for two sprints).
- [ ] Backend: `mypy src/` reviewed. Currently advisory in CI (5
      pre-existing findings, see `docs/AI_HANDOFF.md`) — don't add new
      ones with this change; net-new mypy errors in a diff are worth
      fixing before merge even though the CI gate won't block them yet.
- [ ] Frontend: `tsc --noEmit`, `eslint .`, `next build` all clean
      (`apps/admin-web`).
- [ ] Frontend: Playwright suite passes — `npm run e2e` against a real
      backend (see `apps/admin-web/e2e/README.md`).
- [ ] If any route's request/response shape changed: regenerated
      `docs/api/openapi.json` (`python scripts/export_openapi.py`) and
      committed the diff.
- [ ] If any new environment variable was introduced: added to the
      relevant `.env.example` (`services/api/.env.example` or
      `apps/admin-web/.env.local.example`) with a description, and to
      `docker-compose.yml` if the API needs it to run.
- [ ] If any new database migration was added: hand-written (not
      autogenerated, per Data Architecture v2.0 §7.1), reviewed for
      the RLS/CHECK-constraint patterns the existing migrations use,
      and both `alembic upgrade head` and `alembic downgrade base` were
      actually run against a real database, not just eyeballed.
- [ ] `docs/AI_HANDOFF.md` updated: current step, commit list, test
      status, next task.
- [ ] Manual merge — confirm with whoever's driving before actually
      running `git merge`/opening the PR. This has been an explicit
      "do not merge without asking" branch all sprint; treat that as
      the default going forward, not a one-off for this feature.

## Before promoting `develop` into `main`

Everything above, plus:

- [ ] Full CI run green on `develop` itself, not just the last feature
      branch that landed on it.
- [ ] `docs/AI_HANDOFF.md`'s "Known scope boundaries" and "Pending
      Tasks" sections reviewed — nothing silently regressed since the
      last release.
- [ ] No `# noqa`/`# type: ignore`/skipped-test additions since the
      last release that don't have a tracked follow-up.

## Not yet in place (tracked, not blocking today)

These are real gaps for an eventual production release, deliberately
out of scope for Sprint 4.1's "release hardening" (Step 5) — adding
them means standing up actual staging/production infrastructure and
deployment targets, which is its own decision, not a checklist item to
silently build:

- Staging/production deployment pipeline (Technical Architecture v2.0
  §9.6's later stages: image build + vulnerability scan + registry
  push + staged rollout + manual approval gate + auto-rollback). CI
  today runs tests and builds only; it does not build or publish
  container images.
- A production-shaped `docker-compose.prod.yml` / actual production
  Dockerfile (immutable image, non-root user, multi-stage trim,
  resource limits) — `infrastructure/docker/api/Dockerfile` today is
  explicitly a dev-hot-reload image only.
- Architecture boundary enforcement in CI (import-linter rule failing
  the build if `domain/` imports `infrastructure/`/`presentation/`) —
  documented as a rule (Technical Architecture v2.0 §2.2) but not yet
  machine-enforced.
- Secrets management beyond "GitHub Actions generates a throwaway
  keypair per CI run" and "a committed, clearly-labeled dev-only
  keypair for `docker compose up`" — no secrets manager, no key
  rotation, because there's no real deployment target yet for either
  to protect.
- A CHANGELOG.md / semantic version tags — no release has been cut
  yet.
